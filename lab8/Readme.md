## Завдання 2. Бінарний пошук і чотири поломки

Правильний бінарний пошук на тих самих трьох запитах (вставити вивід):

```
значення X (...): індекс ..., порівнянь ...
перший елемент (0): індекс ..., порівнянь ...
значення, якого немає (21): індекс -1, порівнянь ...
```

Бінарний пошук може повернути будь-який індекс з блоку однакових значень, а не перший:
через повтори індекси лінійного й бінарного можуть відрізнятися, це нормально.

### Поломка 1. `while (lo < hi)` замість `<=`

Останній кандидат, коли лишається одна позиція, ніколи не перевіряється.
На моєму масиві із 100 000 елементів і лише 21 різним значенням **жодне значення не губиться**
(вивід: `... значень, що є, але не знайдені: 0`): кожне значення займає блок із тисяч елементів,
і середина рано чи пізно потрапляє всередину блоку. Поломка проявляється лише на значенні,
що зустрічається один раз. Приклад: масив `{1, 3, 5, 7, 9}`, шукаємо 9: правильний пошук
повертає 4, зламаний повертає -1. Те саме для масиву з одного елемента (див. таблицю крайових
випадків).

### Поломка 2. `lo = mid` замість `mid + 1`

Вхід: шукаємо 21 (відсутнє, більше за всі). Коли лишаються два елементи, `mid` збігається з
`lo`, порівняння дає «менше», і `lo = mid` залишає `lo` на місці. Цикл не завершується.
Щоб це було видно, цикл обмежено 1000 кроків. Вивід (вставити після запуску; очікую
`lo = 99998, hi = 99999` і майже весь ліміт кроків без руху меж):

```
шукаємо 21: результат -1, порівнянь ... (обмеження 1000 кроків)
межі в кінці: lo = ..., hi = ...; кроків без руху меж: ...
```

### Поломка 3. `mid = (lo + hi) / 2`

Сума `lo + hi` переповнює `int`, коли перевищує 2 147 483 647, тобто для масивів, більших
за 2^30 = 1 073 741 824 елементи. Приклад: `lo = 1 500 000 000`, `hi = 2 000 000 000`;
зламана формула дає -397 483 648, а правильна `lo + (hi - lo) / 2` дає 1 750 000 000.
На моїх 100 000 елементів ця версія **працює без жодної помилки**: найбільша сума
`lo + hi` менша за 200 000, до межі переповнення дуже далеко (вивід: `розбіжностей ... : 0`).
Це теж результат: поломка не проявляється на навчальних розмірах.

### Поломка 4. Масив не відсортований

Той самий масив без сортування, 100 запитів значень, які в ньому точно є.
Вивід: `зі 100 запитів наявних значень повернули -1: ...` (вставити число після запуску).

## Завдання 3. Пошук межі (b = 3)

Один метод `FirstWhere<T>(a, pred, out comparisons)` повертає індекс першого елемента, що
задовольняє умову (або `a.Length`). Обидві межі отримано через нього:
`LowerBound(X)` — умова `cmp(e, X) >= 0`, `UpperBound(X)` — умова `cmp(e, X) > 0`.

Основний запит: кількість елементів у [X; Y] = `UpperBound(Y) − LowerBound(X)`.

Вивід (вставити після запуску):

```
LowerBound(X) = ... (... порівнянь), UpperBound(X) = ... (... порівнянь)
елементів, рівних X: ... за ... порівнянь; лінійно: ... за 100000
елементів у [X; Y]: ... за ... порівнянь; лінійно: ... за ...
результати збігаються: True
```

Кількість порівнянь не залежить від того, скільки елементів дорівнює X, бо пошук межі
ділить діапазон позицій навпіл і робить близько log₂(n + 1) кроків, незалежно від довжини
блоку однакових значень.

Умова, не узгоджена з порядком: перший елемент, кратний 7. У відсортованому масиві
умова `e % 7 == 0` чергується: 0 (true), 1–6 (false), 7 (true), 8–13 (false), 14 (true)…
Тому бінарний пошук межі не має на що спиратися: він вважає, що після першого `true`
усе далі `true`, а це не так. Правильна відповідь тут — індекс 0 (число 0 кратне 7).
Вивід програми: `перший елемент, кратний 7: пошук межі дав індекс ..., правильний індекс 0,
збігається: ...`. Висновок: пошук межі коректний лише для умов, які мають вигляд
«спочатку false, далі true» у порядку масиву.

| Запит | Бінарний: індекс / порівнянь | Потрійний: індекс / порівнянь |
|---|---|---|
| значення X | | |
| перший елемент | | |
| значення, якого немає | | |

У середньому по 100 запитах: бінарний ... порівнянь, потрійний ... порівнянь.

Кроків стало менше: ділянка щоразу скорочується втричі, тож кроків близько
log₃(100 000) ≈ 10,5 проти log₂(100 000) ≈ 16,6. Але порівнянь не стало менше:
на кожному кроці потрібно порівняти з двома точками (`m1` і `m2`), тому в гіршому випадку
близько 2·log₃ n ≈ 21 порівняння проти ≈ 17 у бінарного, а в середньому
≈ (5/3)·log₃ n ≈ 17,5 проти ≈ 16,6. Для відсутнього значення 21 (таке гірше за все)
очікую приблизно 21 проти 17: числа з виводу в таблиці це підтверджують (або ні: тоді
так і написати).
